# 一个项目做过以后，下一次能否少走弯路？

状态：本页为已停止采用的 Praxis 选题草案，仅保留此前预检记录。当前选题与协议见 [Werkzeug 外部仓库案例](external-repository-selection.md)，不再按本页启动模型实验。

日期：2026-09-06。English summary: a single-case, frozen-history experiment protocol for experience transfer across two distinct defects in the real Praxis repository. Deterministic defect feasibility is verified; model experiments have not started.

## 研究主张

只做一个有完整证据链的案例，不扩成题库。待检验的主张是：模型完成前序维护工作后，提炼出的项目经验能否帮助它处理同仓库的另一个问题，减少重新探索，同时保持修复正确。

这是一项案例研究，不能证明长期记忆普遍有效。成功应体现为可以从轨迹解释的节省；失败、没有差异或负迁移都保留。预先选定案例，不依据记忆组分数换题。

## 一个真实仓库，两次不同维护工作

使用当前 Praxis 的实际 Runtime、ToolRuntime、WorkflowEffectBroker、WorkflowOrchestrator、SQLite Authority 和 ArtifactStore，不缩成算法模拟器。基线必须保存工作区内容清单与哈希；当前大量修改未提交，单写 git HEAD 不足以复现。

| 阶段 | 对模型描述的症状 | 私有验收关心什么 |
| --- | --- | --- |
| 前序经历 A | 外部工具第一次请求成功后，重用同一请求标识但改变参数，系统仍返回旧成功；相同请求的正常重试也必须保持可用 | 同键同内容仅执行一次；同键不同内容明确冲突；持久化记录不被覆盖 |
| 后续任务 B | 同一工作流先把文件写成 A，再写 B，最后重新写 A，三次都返回成功，实际文件却停在 B | 三个新操作均真实执行；同一操作重试仍重放；同身份改内容仍拒绝；调用身份缺省路径也不误复用 |

A 是受控引入的回归：SQLite reservation 的输入摘要冲突检查被移除。B 复现已审查到的真实历史缺陷：工作区写入的自动幂等键错误地按工具参数内容生成。两处修改分别位于 Authority 与 Broker，不能把 A 的补丁复制到 B 就通过。

A 能产生的有用经历包括：实际执行链怎样连接；如何查看回执与持久化 reservation；输入摘要、请求身份、调用身份各负责什么；怎样同时测试正常重试和冲突；哪条测试命令能覆盖真实文件效果。它不能提前包含 B 的症状、补丁或验收答案。

设计者知道两个缺陷，模型只知道当前任务。不得把本文、私有探针、历史修复报告或实验构造脚本放入模型工作区。

## 固定一次经历，再比较三个条件

1. 在隔离仓库快照中仅引入 A，给 MiniMax 相同的正常仓库搜索、读写和测试能力，让其完成实际排查与修复。学习历史必须是真实执行，不能由设计者预写“经验”。
2. Host 独立验证 A；失败则保留为案例未就绪，不重复生成直到成功。记录完整公开交互及验证范围，不将助手解释视为已验证事实。
3. 从同一公开历史分别生成一次普通 compact 和一次结构化项目经验。后者可以保留定位线索、操作步骤、失败路径、适用条件与实际检查；不是手工填写目标解法。提炼失败计入可用性，不悄悄换快照。
4. 所有目标组拿到完全相同的、已包含 A 修复的代码，然后引入 B；用文件清单/digest 确认一致。无记忆组也享有前序修复，避免混淆代码继承与记忆继承。
5. 创建全新 Session，分别运行无记忆、普通 compact、结构化经验三组。三个配对重复，共九个目标运行；每个重复轮换组别顺序，固定模型/工具/环境，单并发。记忆快照跨重复冻结，不再提炼。

三组都可以重新阅读当前仓库、运行同样的公开测试；不人为隐藏无记忆组需要的信息。唯一计划内差异是继承的上下文。所有组无 Run 轮次、工具次数、累计 Token 或任务截止时间限制，模型上下文与单次输出边界相同。

普通 compact 是必要对照：若两种记忆都同样有效，只能说保留历史有帮助，不能说结构化经验胜过摘要。原始完整历史不列入本次最小实验，属于明确的对照缺口。

## 防止“目标答案已经在仓库里”

当前项目已经修复 B，并有明确描述 B 的回归测试与历史报告，所以不能直接把整个工作目录交给目标 Agent。

在学习开始前固定统一的模型可见文件清单：保留实际实现和普通架构/构建文档，排除实验产物、历史目标修复报告、目标专属验收用例以及可访问这些答案的 git 历史。学习与三个目标组遵守同一规则。B 的修复注释随旧实现复现一并移除，不留下答案提示。

保留的测试须在未引入故障的基线上通过；A 的公开复现测试不能包含 B 的 A→B→A 目标验收。目标专属用例由 Host 保管，模型完成后评分。应报告文件排除清单，不能以此借口给不同组不同仓库。

依赖必须预先准备、版本一致，隔离输出和缓存可写范围；凭据只留在 Provider Host。准备阶段先验证测试与搜索工具可用，不能把依赖安装失败当成记忆效果。

## 怎样才有说服力

**第一层：修复是否成立。** 以独立程序检查为准，不看助手自报成功。验收不仅检查最终文件为 A，还检查重复执行次数、原有重试保证、输入冲突与持久化行为。关闭幂等、绕过 Broker 或直接硬编码结果不能算修复成功。允许不同正确补丁，不按参考 diff 匹配评分。

**第二层：同样正确时，是否少走弯路。** 逐次报告目标执行的模型输入、输出、缓存读取、模型请求数、搜索/读取、失败工具尝试和实际测试调用，展示分布而非只取最好一次。耗时为次指标，受服务端波动影响。错误结果不能凭低 Token 算效率胜出。

**第三层：节省是否来自可观察的经验使用。** 对照公开轨迹与实际注入的 note ID，检查是否复用了先前发现的入口、命令或验证方法，是否减少重复的无效尝试。轨迹只能提供机制证据，不凭模型说“我用了记忆”断言因果。若初步有差异，再单独注册去掉相关笔记的消融；不混进这九次主比较。

**成本口径。** 前序工作作为共同已完成的项目任务，单列实际成本；比较后续任务时，主口径为每次目标执行加该策略一次提炼成本。三次是同一目标的随机重复，不能当成三个真实后续业务任务，把提炼成本除以三来制造收益。真实实验账单与策略反事实成本分开保存。缓存或价格字段缺失就标未知，不把输入+输出直接称为美元费用。

预先固定通过/成本/轨迹三个层面，完整报告所有九个配置。三次重复只帮助识别明显波动，不做总体显著性或跨项目泛化主张。若无记忆三次都迅速解决，结论是这一个案例没有体现价值，不临时增加干扰或剥夺工具来制造优势。

## 已完成的可行性验证

没有调用模型，没有改动主工作区的产品实现。独立副本中的真实文件/SQLite/工具链探针结果：

| 探针 | 预期 | 实际 |
| --- | --- | --- |
| 正确基线：A 与 B 检查 | 通过 | 通过 |

| 恢复 A、只引入 B：新写入与重试检查 | 失败 | 失败 |
| B 存在时重跑 A 检查 | 通过 | 通过 |
| 恢复两个实现 | 通过 | 通过 |

可行性证据：`artifacts/experience-case-preflight-20260906/preflight.json` 及同目录五份日志。构造脚本：`artifacts/preflight-experience-case.mjs`。副本名为 private-probe-workspace，含私有验收，**不是可以直接交给模型的题目工作区**。

这些检查证明两个故障确实可复现、可区分、可验收；不证明模型能修复，也不证明记忆有收益。
