# Plan-and-Review 收敛修复与复杂度判断

> 版本化测评记录：题面、结果和归因对应本文注明的构建与策略，不代表当前默认模式或同版全量成绩。

日期：2026-09-05。本文区分已经修改的实现、已有真实成绩与下一步建议；不把本地回归测试当成 benchmark 提分。

## 结论

先修复确定的框架缺陷，再做少量配对复测，不宜现在继续扩大题库。P&E 对照本身并不过度设计；P&R 值得保留，但不应把每个思考步骤变成强制验收关卡。Plan 是帮助完成任务的可修改工作假设，不是比用户要求更权威的新合同。

这里把“破 plan”理解为计划被新证据推翻、路线失效后的修订或放弃。如果原意只是一般 planning，下面的轻量化原则仍适用。

## 真实证据：代码正确，运行却没能正常结束

- 6 个 Plan Item 已 accepted，Final Review 多次无效响应后 blocked；循环仍把“解释阻塞”提示重新送回模型。
- 9 个失败 Reviewer attempt 没有原始失败诊断，无法事后证明每一个无效响应的具体字段错误。不能全部归因于模型或输出截断。
- 已保存响应显示审查者过度要求“中立”检查者，否定 Agent 自己生成但内容可直接检查的 proto 文件。独立审查不应等于所有证据必须由另一名执行者产生。

因此应分别记录：任务正确性 PASS、Runtime 收尾 FAIL、整次正常完成未成立。压缩成本存在，但本题最直接的浪费来源是控制循环，不是已证实的记忆丢失。

## 本次已经实现的通用修改

| 修改 | 为什么 | 实现位置 |
| --- | --- | --- |
| blocked 成为结构化终态 | 单靠提示模型“停下来”不能控制 Runtime 自己继续循环 | `apps/runtime/src/loop/index.ts`、`framework/runtimeKernel.ts` |
| Reviewer 输出预算随验收条件数增长 | 一条条件与多条带证据解释的条件，不应固定给同样的输出空间 | `review-plan/semanticReviewer.ts`、`reviewCoordinator.ts` |
| 区分截断、格式错误、未确认完成 | 不再把所有失败压成无法诊断的 INVALID | `review-plan/semanticReviewer.ts` |
| 失败 attempt 持久化并可重放 | 重启不能忘记已经付费的失败调用，又发同一次请求 | `review-plan/reviewCallStore.ts`、`reviewCoordinator.ts` |
| 重试携带简短的格式反馈 | 告诉审查者上次错在哪，不把格式错误误当成任务缺陷 | `review-plan/reviewCoordinator.ts` |
| 纠正独立性 Prompt，要求简短证据解释 | 可以检查 Agent 写的代码、选择运行的命令；不能只因 Agent 参与就全盘否定，也不能只信它自述成功 | `review-plan/semanticReviewer.ts` |

blocked 修复发生在 Root 输出无工具最终说明时：结束为 `prompt_blocked / PLAN_REVIEW_BLOCKED`，不再重新追加相同提示。尚可继续执行的未完成计划仍保留继续执行提示；有工具的实际修复不被这个分支提前截断。本次不是添加一个任意轮数上限，也没有取消原有权限校验。

输出上限规则为 `min(32768, max(4096, 2048 + 768 × 条件数))`，再取 Provider 模型上限以内的值。7 条条件得到 7,424 tokens。这是预算策略，不是已经实验证明的最优常数；超多条件仍可能写不完，应首先合并冗余条件，而不是无限放大响应。费用预留与实际请求使用相同规则。

失败记录区分 `provider_invalid`（已收到 completed，但响应不可用）与 `provider_unknown`（无法确认完成）；保存错误码、阶段、校验路径、可取得的响应摘要哈希/字节数、停止原因和用量完整性。不保存失败原文，所以可定位格式边界，但不能凭摘要还原模型原话。对于中途断流，仍保守处理未知费用，不伪造精确账单。数据库增加可空字段，兼容原有记录。

Prompt 全文、重试动态字段、预算和状态分支已同步到 [模型请求目录 M11](../../model-request-catalog.md#9-m11reviewplan-semantic-reviewer)。

## P&E 到底重不重

当前实验的 P&E 实现在 `D:\agent-evals\adapters\harbor_praxis.py`：同一个 Praxis AgentLoop，通过 Prompt 要求先列文字计划、按计划执行、必要时修改并最终自检，禁止调用 `plan.*`。它是轻量的实验控制组，不是某个工业平台完整 P&E 引擎的复刻。

本地历史 P&E 有 12 个 rollout、11 道不同题，11 次正常完成中 4 次通过；另一个 G-code rollout 被人为中止用于诊断。这个数字包含重复题、历史低分选样和不同版本，不能当作严格成功率，更不能用来证明所有 P&E 方案都差。

P&R 更重的部分是 Item/Attempt、冻结证据、逐条件说明和语义重试。持久化事实、避免重复执行、检查原始任务是否被偷换，有明确价值；但“读环境 → 安装依赖 → 看源码”若分别要求完整语义验收，就可能让模型花更多时间解释流程，而不是交付结果。

没有必要现在删除恢复机制或再引入 DAG。优先改变计划粒度：用少量可交付结果作为里程碑，在里程碑内部保留自主工具循环。独立审查应回答“这一阶段的结果可靠吗”，不是检查模型是否遵守了它自己预先想出的每个动作。

## 工业界公开实践与可借鉴部分

不存在一套所有产品统一采用的 planner 标准，以下是可核查的公开实现或实验，不代表整个行业。

1. **轻量可变计划。** LangChain Deep Agents 的当前文档把任务规划列为可选能力，使用待办状态管理进度，并将 subagent 委派与规划分开。Praxis 可以借鉴“规划按需启用”，无需为了拥有 subagent 强制使用 ReviewPlan。[官方文档](https://docs.langchain.com/oss/python/deepagents/overview)
2. **按实际产出评估，而非过早固定实现细节。** Anthropic 2026-03-24 的长期应用开发实验采用 planner、generator、evaluator；规划保持较高层次，按功能阶段执行，评估使用实际应用交互。它也随模型能力变化移除了部分旧控制机制。值得借鉴的是粗粒度验收与实证删减复杂度，不是照抄三种固定角色；该实验针对应用开发，不能直接证明通用任务收益。[原文](https://www.anthropic.com/engineering/harness-design-long-running-apps)
3. **反馈有价值才增加循环。** Anthropic 的通用工程建议强调从简单方案开始，利用环境反馈推进，遇到阻塞请求帮助；evaluator-optimizer 适合验收标准清晰、反馈确实能够改善结果的任务。Reviewer 不是加了就必然更准。[原文](https://www.anthropic.com/engineering/building-effective-agents)

据此对 Praxis 的建议是推论，而不是来源承诺：保留“自主执行＋可选计划＋关键点审查”，避免“每个动作审批＋不断自证”。

## 计划失效后应该怎样处理

| 观察到的情况 | 合理动作 | 不应该做的事 |
| --- | --- | --- |
| 路线仍正确，只是实现有 bug | `needs_fix`，修复当前工作并补证据 | 重建整份计划 |
| 假设被推翻、方法不适用、模型自己写错验收条件 | `replan`，修改受影响计划和条件 | 为了通过错误条件而破坏正确实现 |
| 只是证据不够或被截断 | 读取冻结证据或补最小必要检查 | 凭空要求大改代码或另起一个“中立”执行者 |
| 外部资料、权限或环境不可得 | `blocked`，说明缺什么并结束等待 | 反复解释、猜答案、降低用户要求后宣布通过 |
| 计划本身不再值得维护 | 在策略和授权允许时 abandon，继续适合的执行模式 | required 模式中绕过验收 |

当前 `PlanControlServiceV1.update` 已有 revision、无变化检测、在途 Attempt/fence 冲突检查和重规划预算。它不是完全无约束地随时改：有 open/review_requested Attempt 时必须先处理在途状态。`abandon` 需要控制授权，required 策略拒绝放弃。本次没有放开这些边界，以免把“纠正路线”变成“跳过验收”。

进一步简化的候选是：减少中间语义检查、按未解决风险选择检查点、显式说明改计划对旧证据的影响。但尚未实现，也未证明哪一种策略最优；不能在文档中将这些建议冒称现有能力。

## 新手术语

- **rollout**：模型从接到题目到结束的一次完整尝试，同一道题可以有多次。
- **里程碑 / Item**：一阶段可描述、可检查的交付结果，不必是一条工具调用。
- **Attempt**：某个步骤的一次执行尝试；修正后可以有新尝试。
- **fence（围栏）**：防止验收期间证据与计划被同时改动的保护状态。
- **digest**：内容的哈希指纹，用来判断内容是否相同，不证明内容正确。
- **oracle/verifier**：外部验收程序；此处指 benchmark 官方测试，不是 Reviewer 自己的评价。
- **收敛**：任务完成或明确受阻后能真正结束，不无限循环。
